# Status

What works today, how each claim is checked, and what is known to be wrong or
missing. Last revised 2026-10-19.

Every design the generator can produce is at one of three levels.

## Level 1: signoff-clean on GF180MCU

One design: **Block A, the GF180MCU reference design**
(`configs/mosaic_tapeout_ultra.yaml`, wrapper `mosaic_block_a`).

- Two SERV harts (one orchestrator, one worker), no on-chip SRAM pool, a
  128-byte scratchpad, a 1 KB boot ROM, code executed in place from external
  flash, one UART, the TDU, no DMA, no debug module, no PLIC.
- Run `blocka_d15_rstsync`: a 1110 um square die (1.2321 mm2), 82.9%
  utilisation, hardened against an external padframe DEF. Magic DRC, KLayout
  DRC, LVS, XOR, routing DRC, antenna and power-grid checks are all at zero.
  Setup slack is +2.199 ns and hold slack +0.054 ns at the worst corner on a
  50 ns clock, with no maximum-transition or maximum-capacitance violations.
- Two waivers are recorded for it in `flow/librelane/signoff_waivers.yaml`: two
  clock-tree root buffers above the project's fan-out limit, and eleven unused
  input terminals of output-only pads. Both are pinned to the exact violators
  and are due for review on 2026-11-30.
- The waiver record states that gate-level simulation of this netlist passed.
  That log is not in version control.

This is the only combination that `soc.target: tapeout` accepts.

## Level 2: hardened but not tapeout-qualified

**Block B** (three SERV harts) and **Block C** (four SERV harts), the same
architecture as Block A with more workers.

- Both have runs that pass every hard check, timing and the transition and
  capacitance gates: `blockb_sdc`, `blockb_m45`, `blockc_sdc`, `blockc_m45`.
- Both report fan-out violations that no waiver accepts, and neither is in the
  tapeout matrix of `core_registry.py`, so `target: tapeout` refuses them.
- Later runs recorded in the source tree, but not tracked, show Block C routing
  at a 0.74 utilisation target on 1.9959 mm2 and Block B closing at 20 MHz.

The measured numbers and run names are in
[physical-flow.md](physical-flow.md#measured-results).

## Level 3: RTL and simulation only

Everything else:

- every core other than SERV;
- the `log` and `floonoc` bus fabrics;
- every design with an on-chip SRAM pool or external RAM;
- every design that keeps the DMA, the debug module or the PLIC;
- every design on `pdk: sky130` or `pdk: ihp-sg13g2`.

Simulation coverage differs by feature, and some of these have none. The
gaps are listed under [Known defects and gaps](#known-defects-and-gaps).

The IHP sg13g2 technology is declared in the technology store
(`harness/physical/technology.py`) with its site geometry and corner names, a
probe configuration (`configs/mosaic_ihp_probe.yaml`) and an unqualified signoff
template. `./mosaic pdk-port ihp-sg13g2` reports five of eight porting
requirements missing, starting with an area calibration from a hardened run.
For sky130, none of the eight is satisfied.

## What is proven, and how

| Area | Claim | How it is checked |
|---|---|---|
| Generation | One YAML file yields RTL, linker scripts, a boot manifest and a testbench in a bundle named by a hash of its inputs. | `make mosaic-gen`; `test_build_manifest.py` and the generator tests in `test/test_mosaic_gen/` |
| Validation | A configuration is refused before anything is generated if it breaks a rule. | `core_registry.py`; `./mosaic tb-matrix run --tier validate` over 248 configurations |
| Cores | Ten cores run a liveness program in the complete SoC: cv32e20, cv32e40x, serv, fazyrv, picorv32, snitch, hazard3, cva6, rocket, boom. | the `wake_*` and `titan_smp_*` steps of `scripts/run_sweep.sh` |
| Fabrics | The wake demonstration and the four-hart multiprocessor run on `obi`, `log` and `floonoc`. | sweep steps `wake_obi`, `wake_log`, `wake_floonoc`, `titan_smp_*` |
| TDU | Register access at the SoC address, a queue of up to three entries, per-hart wake. | `tb/tdu/soc`, `tb/mosaic/cocotb`, the full-SoC benches |
| DMA | As a block, the iDMA wrapper copies in one dimension on both streams and in two and three dimensions on stream 0. | `tb/idma/cocotb/run.sh` |
| eFPGA fabric | One FABulous 2.2.0 fabric preset (64 LUT4) is generated by pinned tools and, alone, runs the real bitstream of an 8-bit counter. | sweep step `efpga_fabric` (`tb/efpga/run.sh`, Icarus and Verilator, 12 negative controls in 16 runs); `test_efpga_fabric.py` |
| eFPGA as a bus peripheral | `hw/efpga/mosaic_efpga.sv` wraps the fabric with a configuration loader, an unload for designs that have run, isolation and a bus timeout. `soc.efpga` puts it and the fabric of a preset in the generated SoC. Firmware on the wake-demonstration SoC with the key loads a bitstream through its registers, uses two registers of the user design, unloads it and loads it again; the production firmware loads a design from its flash image at cold boot, through the driver `sw/firmware/common/efpga.h`, before it wakes the workers. A user's Verilog written against the shell of the preset goes to such a boot in one command (`EFPGA_DESIGN` of `run_fw.sh`); after a warm reset the firmware first removes the design the fabric kept, with its unload stream from flash. | sweep steps `efpga_wrapper` (`tb/efpga/run_wrapper.sh`, Icarus and Verilator, 46 negative controls in 50 runs), `efpga_soc` (`tb/mosaic_soc/run_efpga.sh`, six firmware runs, four of them controls) and `efpga_design` (`run_fw.sh` with `tb/efpga/shell_regs.v`) |
| Memory profiles | An SRAM pool, and execute in place with a scratchpad, boot in simulation. Execute in place without a scratchpad and external RAM only validate. | sweep steps `wake_*`, `firmware_7hart`, `generic_boot_blocka`; `test_external_memory_profile.py` checks that software generation refuses the other two |
| Firmware | A deployable flash image boots the default seven-hart design. | sweep step `firmware_7hart` |
| Any SoC the generic bench accepts | Every configured hart must report before the bench passes. | `tb/mosaic_soc/run_generic.sh`, in the sweep on Block A only; the `tb-matrix` `sim` tier of 30 configurations is not part of the sweep |
| Physical flow | No step is skipped and a missing metric is not read as clean. | `flow/librelane/experimental/run_signoff.sh`; `harness/evidence/` and its tests |
| Reproducibility | The simulation and physical toolchains are pinned to the same nix-eda and nixpkgs revisions. | `flake.nix`; `test_toolchain_pin.py`; `./mosaic doctor` |
| Agent tooling | Tools reach the flows only through typed, gated calls. | `harness/gates.py`; `test_mcp_plugin_mode.py`, `test_agent_runtime.py` |
| Python suite | 1791 passed, 99 skipped. | `make test` |

The sweep steps are defined in the repository; their results depend on running
them with the pinned toolchain ([verification.md](verification.md)).

## Known defects and gaps

Cores and fabrics:

- **QERV** is exercised only inside the CPU subsystem testbench, not in the
  complete SoC.
- **Ibex** appears only in a configuration that is rendered, never simulated.
  **cv32e40p** and **cv32e40px** have no shipped MOSAIC configuration. All three
  are accepted by the generator and unproven.
- **CVA6, Rocket and BOOM** are simulation only and cannot enter a GF180MCU
  layout.
- Only the `obi` fabric has been through the physical flow.
- Six peripherals can be requested. The underlying platform has more that the
  configuration cannot name.

Verification:

- **Gate-level simulation is functional only.** The GF180MCU cell models cannot
  be timing-annotated under Icarus Verilog. A GLS pass is reported but is not a
  signoff hard check.
- **Equivalence checking** is wired as the `lec` flow and does not yet return a
  usable verdict.
- The `tb-*` flows have timeouts shorter than the RTL generation they can
  trigger on a cold build directory, so the first run can time out.
- **Boot from SRAM is untested.** Every bench that runs from SRAM has the
  testbench write the program into the RAM and set the boot ROM's exit flag.
  The boot ROM's copy from flash to RAM (`boot_select=1` with
  `execute_from_flash=0`) is selected by no runner.
- **The orchestrator firmware's SRAM builds are neither built nor simulated by
  a regression step.** `make` and `make demo` in `sw/firmware/` without a
  bundle, and the scheduling demo with one, link `sw/firmware/titan/start.S`
  without `MOSAIC_FLASH_XIP`. In that form the file sets no stack pointer and
  no global pointer and clears no `.bss` before it calls `main`. Only the
  `firmware-build` and `firmware-demo` flows build them, on demand. The image
  that is run is the execute-in-place one (`tb/mosaic_soc/run_fw.sh`).
- **The generated C start-up code runs nowhere.** No program in `sw/firmware/`
  or `tb/mosaic_soc/` links `startup/image_<n>_crt0.S`.
- **Five of the six peripherals have no test.** Only the UART is driven by a
  program (`tb/mosaic_soc/run_uart.sh`, on Block A): polled transmit and
  receive through the internal loopback, not the receive pin or the
  interrupts. GPIO, the timer and the SPI host are built into the simulated
  designs and never touched. I2C and the serial link are requested by no
  shipped configuration and are in no design the sweep builds.
- **The always-on blocks have no test**: the always-on GPIO and timer, the
  fast interrupt controller and the power manager, of which the boot ROM reads
  one register.
- **No hart takes an interrupt.** No program in `tb/mosaic_soc/` or
  `sw/firmware/` sets a trap vector, so delivery through the CLINT and the
  PLIC is untested in the complete SoC. The register-level testbenches of the
  CLINT and the TDU (`hw/tdu/tb/`) have no runner.
- **The TDU is tested with up to three queued tasks.** The full queue of
  eight, the TDU interrupt, and parking a hart then waking it again are not.
- **The core tests are liveness tests.** The wake and SMP programs are a few
  RV32I instructions per hart. They use neither the M or C extensions nor
  RV64, and on `log` and `floonoc` they reach only SRAM, the TDU and the SoC
  controller.
- **The JTAG debug module is untested.** It is on by default, and every bench
  disables the simulation JTAG bridge (`JTAG_DPI=0`).
- **Two memory profiles cannot be simulated.** For external RAM, and for
  execute in place without a scratchpad, the configuration validates and
  software generation then refuses it, so no bundle is produced.
- **`soc.dma: xheep` does not select X-HEEP's DMA.** A one-hart design
  generated with it contains the iDMA wrapper. No test covers the value.
- **Three software tests depend on a compiler the pinned shell does not
  provide.** They look for `riscv64-unknown-elf-gcc`; the pinned toolchain is
  `riscv32-none-elf`. Without the other compiler one test is skipped and two
  pass without compiling anything: the worker assembly, the `titan_main.c`
  compile, the generated start-up code, the bundle firmware build and the
  checks on the packed flash image do not run.
- **The sweep is run by hand.** There is no continuous integration. For the
  full-SoC steps other than `efpga_soc` and `efpga_design` the sweep's
  success marker also matches the line a runner prints on failure, so there
  the exit status alone decides.

eFPGA ([efpga.md](efpga.md)):

- **The fabric is in one simulated SoC, on one bus.** `soc.efpga` takes only
  `bus: obi`, and only the wake demonstration with the key has been
  simulated. The fabric's pads stay inside the SoC, and there is no layout;
  the wrapper was never synthesised. The command from a user's Verilog to a
  simulation shows that the design is loaded and configured, not that it
  works: no firmware of the user's uses it.
- **`clear` is unsafe on a design that has run.** It zeroes every latch at
  once, and with one of the two test designs both simulators stop. The
  design's unload stream removes it instead, and a reset keeps it. A reset
  keeps a fabric only when 48 latches agree on a tag and its check, which
  latches that start at random do about once in 2^32; otherwise it clears
  them, as it did before.
- **Loading is safe only in the order the generator writes.** In `bit_gen`'s
  own order one of the two test designs oscillates half-way. The order the
  generator uses instead is argued from the RTL of the tiles, not proved,
  and the loader does not check it. A frame goes into the latches only after
  its check word: of 70 single-bit flips tried once, none stopped the
  simulator, where one of 70 did before the check words.
- **A pad the user design does not bind is driven**, with an output enable
  that follows the design's internal signals. The wrapper has no mask for the
  pads, and the SoC test leaves them unconnected.
- **One preset, three user designs and one core are tested**: `small`, an
  8-bit counter on the pads, two registers on the east edge, and the shell
  example, which is only loaded; a cv32e20 loads them, from SRAM and from
  flash. A wrong configuration bit in a resource a design does
  not use is not detected. The wrapper cannot master the bus and raises no
  interrupt.
- **Larger fabrics are unmeasured in the sweep.** The fabric of FABulous's
  default template did not build with Verilator on the development machine
  (`std::bad_alloc` at 4.0 GB).
- **Verilator simulates the fabric with every latch starting at 0.** With
  latches that start at random the simulation does not converge.
- **Place and route of a user design gives no timing result.** The delays the
  pinned nextpnr 0.9 uses are placeholders, the same for every LUT and every
  routing switch, so the frequency it prints is not a result. FABulous's own
  environment pins other Yosys and nextpnr revisions.
- **`./mosaic doctor` does not check the eFPGA tools.** The generator
  refuses other versions itself.

Physical:

- **Power is a proxy.** Energy per cycle is computed from the timing tool's
  default switching activity, not from a simulated workload.
- **The area model and the routability records are GF180MCU only**, and cover
  only SERV designs of 2 to 4 harts.
- **The routing guard** recognises a plateau only after it has happened; it does
  not predict one before routing starts.
- **The chip-level flow has no inputs.** `make harden` and `make classic` in
  `flow/librelane/` need a physical bundle with SRAM macro views and a bound
  pad adapter that the repository does not contain.
- **The Block A fan-out waiver names a pre-rename instance.** Its two violator
  names start with `clkbuf_0_i_core_v_mini_mcu`, as in the netlist of
  `blocka_d15_rstsync`. The wrapper now names that instance `i_mosaic_soc`, so
  the names have to be re-based on the next Block A run. The signoff gate
  compares violator names only for disconnected pins; for this waiver the
  check that reports a difference is `./mosaic waiver-author`.

Tooling:

- The unit benches `tb/tdu/soc/cocotb` and `tb/idma/cocotb` compile register
  packages that only the legacy in-place generation writes, so they need
  `make mcu-gen` once before they run in a fresh clone.
- **`make mcu-gen` ends in an error.** It renders the templates and runs the
  register generators, which is what those two benches need, and then stops
  with `Cannot find floo_mosaic_noc_pkg.sv`. `make verilator-build`, the
  legacy single-core simulation build, fails on the same file while its exit
  status is 0, and the `verilator-lint` flow, which runs that target, judges
  it by the exit status.
- `./mosaic pdk-port` reports GF180MCU as incomplete until the PDK has been
  cloned with `make -C flow/librelane clone-pdk`.
- Model-driven use of the plugin has been checked by handshake and by the test
  suite, not by a live model session in every host
  ([agent-harness.md](agent-harness.md#host-plugins)).
