# eFPGA fabric

MOSAIC-SoC is gaining an embedded FPGA: a reconfigurable block generated with
[FABulous](https://github.com/FPGA-Research/FABulous), meant as a peripheral on
the bus and as a worker beside the cores. This page states what exists. The
phases that do not exist yet are in [roadmap.md](roadmap.md).

## What exists

One fabric can be generated by pinned tools. It is simulated alone, inside a
wrapper that makes it a bus peripheral, and inside a generated SoC whose
firmware loads it, unloads it and loads it again. The configuration key
`soc.efpga` puts it in the SoC:

| Part | File |
|---|---|
| The fabric preset `small` | `configs/efpga/small.csv` |
| The generator, which runs FABulous, Yosys, nextpnr and `bit_gen` | `util/mosaic_gen/efpga_gen.py` |
| The tool shell | `nix develop .#efpga` (`flake.nix`, `util/efpga-requirements.txt`) |
| The wrapper: loader and unload, isolation, bus timeout | `hw/efpga/mosaic_efpga.sv` |
| The key, and a SoC that has it | `soc.efpga` in `util/mosaic_gen/core_registry.py`; `configs/mosaic_efpga_demo.yaml` |
| Two user designs, and the benches of the fabric and of the wrapper | `tb/efpga/` |
| The driver, and the load at cold boot | `sw/firmware/common/efpga.h`; `cold_boot.c` and `util/mosaic_gen/pack_flash.py --efpga` |
| The shell, and the command from a user's Verilog to a simulation | `efpga_gen.py --shell`; `EFPGA_DESIGN=<design>.v tb/mosaic_soc/run_fw.sh` |
| The firmware and the runner of the SoC test | `tb/mosaic_soc/prog_efpga/`, `tb/mosaic_soc/run_efpga.sh` |
| The regression steps | `efpga_fabric`, `efpga_wrapper`, `efpga_soc`, `efpga_design`, `efpga_log`, `efpga_floonoc`, `efpga_serv` in `scripts/run_sweep.sh` |

What does not exist: pads of the fabric outside the SoC, a second preset, and
a layout. The wake demonstration with the
fabric has been simulated on each of the three buses, and the wrapper was
never synthesised. A design is replaced through its unload stream; `clear` does not
remove a design that has run safely, and a reset keeps it ([Limits](#limits)).

## The preset `small`

A preset is a FABulous `fabric.csv`. The tiles are the ones FABulous 2.2.0
ships in its project template.

| | |
|---|---|
| Shape | 4 logic rows of `W_IO`, `LUT4AB`, `LUT4AB`, `RAM_IO`, between two terminal rows |
| Logic | 64 LUT4, each with a flip-flop (8 `LUT4AB` tiles of 8) |
| Pads | 8 bidirectional pads on the west edge |
| East edge | 4 `RAM_IO` tiles: 64 inputs, 112 outputs and 16 configuration outputs. The bench of the fabric leaves them unused; the wrapper uses 47 inputs and 33 outputs |
| Configuration | 6,696 latches; a bitstream has 80 frames, one per strobe line, and is 1,624 bytes |

## Generating a fabric and bitstreams

```bash
nix develop .#efpga
python3 util/mosaic_gen/efpga_gen.py --preset configs/efpga/small.csv \
    --out build/efpga/small \
    --design tb/efpga/counter8_en.v --wrapper tb/efpga/counter8_en_wrapper.v \
    --design tb/efpga/bus_regs.v --wrapper tb/efpga/bus_regs_wrapper.v
```

The shell provides no Python: `python3` is the host's or the sim shell's, and
the generator needs only the standard library. `--design` and `--wrapper` go
together, once per user design, and are optional; without them only the
fabric is generated. A design's wrapper is a module `top_wrapper` that binds
it to cells of the preset: the pads, the clock, the east edge. The output
directory is deleted first and then holds:

| Path | Contents |
|---|---|
| `proj/` | the FABulous project: `Fabric/eFPGA.v`, `Tile/`, `.FABulous/` |
| `fabric.f` | the Verilog files of the fabric core `eFPGA`, one per line |
| `efpga_inst.vh` | the instance of the core with its port map, cut from FABulous's `eFPGA_top.v`. The wrapper and the bench of the fabric include it, so neither can drift from the generated fabric |
| `bitstream/` | per design: the netlist, the FASM (nextpnr's, then the lines of the design's tag), `bit_gen`'s `.bin` bitstream and other outputs (`.csv`, `.vh`, `.vhd`), the log of each tool, `<design>.hex`, the words the wrapper's loader takes, one per line, and `<design>.unload.fasm`, `.unload.bin` and `.unload.hex`, the stream that removes the design |
| `load_order/` | `registered.bin`, the bitstream that only switches every logic cell to its flip-flop output, and `tagged.bin`, the one that sets every latch of a tag and its check ([the order of the frames](#the-order-of-the-frames)) |
| `manifest.json` | the sha256 of the preset, the designs, their wrappers and the requirements file; the path of each tool that ran and the version FABulous, Yosys and nextpnr-generic reported; the geometry; the tag of each design; the sha256 of every file in `fabric.f`, of `eFPGA_top.v`, of `efpga_inst.vh`, of `registered.bin`, of `tagged.bin` and of each `.bin` and `.hex` |
| `*.log` | the output of FABulous |
| `home/` | the `HOME` the tools ran with |
| `.efpga_gen` | the mark by which the generator recognises a directory it made |

Nothing generated is committed. The generator stops unless FABulous, Yosys and
nextpnr-generic report the pinned versions and `bit_gen` is on `PATH`. It
checks this before it creates or deletes anything, and it refuses to delete a
directory it did not make. Two runs give the same fabric and the same
bitstream, bit for bit: compare the `outputs` of their manifests.

**No PDK is involved, and FABulous must be kept away from one.** FABulous
installs a PDK through ciel under `$PDK_ROOT`, or under `~/.ciel` when that is
unset, on any project command once `FAB_PDK` is set, and its `create-project`
always sets it. No PDK is needed to generate or simulate a fabric. The
generator therefore runs every tool without the inherited `PDK*`, `FAB_*` and
`XDG_*` variables and with `HOME` inside the output directory (nextpnr gets
only the `FAB_ROOT` the generator sets), removes the `FAB_PDK` line from the
project, and fails if a tool reports using a PDK. The `FABulous` command of
the shell also drops the PDK variables. Run by hand it can still download a
PDK, into `~/.ciel`: generate fabrics through the generator.

## In a generated SoC

```yaml
soc:
  efpga:
    preset: small    # configs/efpga/<preset>.csv
```

With this key the generator puts the wrapper and the fabric of the preset in
`mosaic_soc`:

| What | Where |
|---|---|
| The registers (`BITSTREAM`, `STATUS`, `CONTROL`, `TAG`) | `0x200C_0000`: the always-on peripheral `efpga` of `configs/general.hjson` |
| The user window | `0x5000_0000`, 4 KB: a slave of the system crossbar |
| The fabric | `<bundle>/generated/efpga/`: `efpga_gen.py` without designs |
| The addresses, for firmware | `MOSAIC_EFPGA_BASE`, `MOSAIC_EFPGA_WINDOW_BASE` and `MOSAIC_EFPGA_WINDOW_SIZE` in `mosaic_memory_map.h`; `MOSAIC_ASM_EFPGA_BASE` and `MOSAIC_ASM_EFPGA_WINDOW_BASE` in `mosaic_memory_map.inc` |

The always-on domain is neither clock-gated nor power-gated. The wrapper takes
the reset of the bus (`rst_n_sync && debug_reset_n`), out of which it keeps a
tagged design. Its pads stay inside the SoC: `pad_in_i` is 0 and the outputs
go nowhere.

`mcu_gen.py` calls `efpga_gen.soc_fabric` before it renders the templates,
which need the fabric's geometry. That function enters `nix develop .#efpga`
when FABulous is not on `PATH`, and keeps a fabric already in the bundle: the
bundle's key covers the preset, the generator and the requirements file, and
`manifest.json` is written last. It writes `soc.f`, the Verilog of the fabric
and the wrapper. The build manifest names `soc.f` as an ordered filelist
fragment and its directory as an include root (`efpga_inst.vh`), and records
the hash of each of those files, which FuseSoC staging checks.

On the `log` and `floonoc` buses the user window is the sixth slave of the
non-memory tier (`NONMEM_EFPGA_WIN_IDX`); FlooNoC's peripheral endpoint
already covers every address above the SRAM. Refused, each by name: a base
configuration without the always-on peripheral `efpga`, and
`mcu_gen.py --legacy-in-place`. The tapeout rules do not name the key; the
physical flow refuses a design with a fabric when it lists its files, since
the wrapper has never been synthesised.

### Booting with a design

The production firmware (`sw/firmware`, [DEPLOYMENT.md](../sw/firmware/DEPLOYMENT.md))
loads a design from flash before it wakes the workers:

```bash
make -C sw/firmware MOSAIC_GENERATED_ROOT=<bundle>/generated \
    EFPGA_STREAM=$PWD/build/efpga/small/bitstream/bus_regs.hex
```

`pack_flash.py --efpga --efpga-unload` puts the design's unload stream and
then its stream after the worker images, as the last two entries of the
deployment table. Since these entries, every entry starts with its kind, and
the table is version 2: kind 0 is an image TITAN copies to SRAM and checks,
kind 1 a stream it writes to `BITSTREAM`, kind 2 the unload it writes before
it, only when `TAG` is not 0. That happens after a reset that kept power: the
fabric still holds the design that ran, and the loader takes only that
design's unload ([the wrapper](#the-wrapper)). The boot manifest of a design
with `soc.efpga` names the register address, and the packer refuses a stream
for a design without one, a stream without its unload, and a table longer
than the 15 entries TITAN takes. TITAN's cold-boot code writes the streams
with the driver, `sw/firmware/common/efpga.h`, and connects the fabric only if
the loader reports `configured`; it does not check the entries' CRC, since
the loader checks every frame and each stream's own CRC. A refused stream
leaves the fabric isolated, and the boot goes on without it: the workers run,
and the exit value is then the `STATUS` of the refusal with bit 31 set. If
the fabric holds another design than the one packed, after a reset, its
unload is refused and so is the load: only a power cycle or that design's
unload clears it.

`efpga.h` is the driver for any C firmware on such a design: the register and
bit names, `mosaic_efpga_load`, which writes a stream (a design or its unload)
and returns `STATUS` once the loader is idle, `MOSAIC_EFPGA_LOADED` and
`MOSAIC_EFPGA_EMPTY`, which tell from that `STATUS` whether a design is in the
fabric (the sticky `timeout` and `blocked` flags survive a load), and
`mosaic_efpga_connect`.

### A user's design

A design written against the shell needs no top_wrapper: a Verilog module
named after its file, with any of these ports and no other.

| Port | Direction, width | Meaning |
|---|---|---|
| `clk` | input | the fabric's clock, stopped while it is cut off |
| `rst_n` | input | the user reset, low while `CONTROL` holds it and while the fabric is cut off |
| `valid`, `we`, `be[3:0]`, `addr[7:0]`, `wdata[31:0]` | input | a request of the user window: `addr` is the word address, byte address `[9:2]` |
| `ack`, `rdata[31:0]` | output | its answer, in the handshake [the wrapper](#the-wrapper) describes |
| `io_in[7:0]` | input | the pads, 0 while they stay inside the SoC |
| `io_out[7:0]`, `io_oeb[7:0]` | output | the pads, `io_oeb` low driving one; the two go together |

`efpga_gen.py --shell <design>.v` reads the ports with Yosys and writes the
top_wrapper, `<design>.shell.v`, which puts each port bit on the cell and pin
of the edge the wrapper drives. Without `ack` the shell holds it low, so the
wrapper's timeout answers every request; without `io_oeb` it holds every pad
released. Any other output of the fabric a design leaves unbound would follow
its default route ([Limits](#limits)). `efpga_gen.py --fabric <bundle>/generated/efpga`
compiles for the fabric already in a SoC's bundle instead of generating one.
The one command from a user's Verilog to a simulation:

```bash
MOSAIC_CFG=configs/mosaic_efpga_demo.yaml EFPGA_DESIGN=my_design.v \
    nix develop .#sim --command tb/mosaic_soc/run_fw.sh
```

It generates the SoC, compiles the design for its fabric, packs the stream and
its unload into the production firmware's flash image and boots it from
flash. `WARM_REBOOTS=1` resets the SoC after the first boot, as a reset pin
would, and boots again from the same flash with the design still in the
fabric (`+warm_reboots` of `tb/tb_top.sv`). `EXIT SUCCESS`
means that the design synthesised, placed and routed, that the loader took its
stream and reported `configured`, that TITAN connected it, and that the
workers then ran.

`EFPGA_TEST=my_test.c` adds the check of what the design does: a C function
`uint32_t efpga_test(void)`, compiled into TITAN's image with the driver's
header, which TITAN calls once the workers ran, on every boot. It returns 0
when the design passed; any other value ends the run with `0x4000_0000` and
that value. Through the flow runner the same is `EFPGA_DESIGN=my_design.v
EFPGA_TEST=my_test.c ./mosaic flow-runner run tb-soc-fw --config
configs/mosaic_efpga_demo.yaml`. The example is `tb/efpga/shell_regs.v`, one
register written byte by byte, on the bus and on the pads, and its check
`tb/efpga/shell_regs_test.c`: the register's reset value, a word, a byte,
every data line each way, and no request left unanswered.

## How the fabric is configured

The fabric core is the module `eFPGA`. Each of the eight pads has an input
`O_top` (pad to fabric), two outputs `I_top` and `T_top` (fabric to pad, and
its output enable) and four `config_C` outputs. The other ports are the
`RAM_IO` edge of the table above and three inputs, described here for a
fabric of `R` logic rows and `C` columns:

| Port | Width | Role |
|---|---|---|
| `FrameData` | `32 * (R + 2)` | row `Yn` takes bits `[32n +: 32]`; `Y0` and `Y(R+1)` are the terminal rows and hold no configuration |
| `FrameStrobe` | `20 * C` | column `Xc` takes bits `[20c +: 20]` |
| `UserCLK` | 1 | the clock of the user design |

There is no reset and no configuration clock. Every configuration bit is a
latch whose data is one `FrameData` bit of its row and whose enable is one
`FrameStrobe` bit of its column. It is transparent while the strobe is high.

A `bit_gen` bitstream is a sequence of big-endian 32-bit words:

1. four header words, then the sync word `0xFAB0FAB1`;
2. one frame per strobe line: a header word, with the column in bits `[31:27]`
   and a one-hot strobe mask in bits `[19:0]`, then `R` data words, the first
   for row `Y(R)` and the last for row `Y1`;
3. a final word with bit 20 set.

To load a frame, put the data words on `FrameData`, raise the masked strobe
bits of the column, lower them, and only then change `FrameData`: the data
must be held across the falling edge. The bench of the fabric does exactly
this, and so does the wrapper's loader. Both ignore header bits `[26:21]`;
the bench skips the four header words, and the wrapper's streams leave them
out.

## The wrapper

`hw/efpga/mosaic_efpga.sv` contains the fabric core and a hard part that always
answers. FABulous's `eFPGA_top` and its configuration logic are not used. The
module has a register port (`reg_req_t`), one OBI slave port for the user
design, and the eight pads. Its parameters are the geometry of the preset and
two timeouts.

| Offset | Register | Access | Contents |
|---|---|---|---|
| `0x0` | `BITSTREAM` | write | the next word of a stream: a `<design>.hex` of the generator, or the `<design>.unload.hex` of the design in the latches |
| `0x4` | `STATUS` | read | `[0]` busy, `[1]` configured, `[2]` error, `[10:8]` its cause |
| | | write 1 to clear | `[3]` timeout: the user design did not answer; `[4]` blocked: an access while isolated |
| `0x8` | `CONTROL` | read, write | `[0]` isolate and `[1]` user reset, both 1 after reset |
| | | write | `[2]` clear: forget the configuration and start again |
| `0xC` | `TAG` | read | `[15:0]` the tag of the design in the latches, 0 when there is none |

A write that does not carry all four bytes is dropped, so a byte or half-word
store changes nothing. A flag that is set in the cycle in which its bit is
written stays set. The register port never reports an error: the SoC discards
that signal. The four registers repeat every 16 bytes, and `TAG` takes no
write.

**Streams.** A stream is the words written to `BITSTREAM`, one per write:

1. the sync word `0xFAB0FAB1`, and in an unload the word `0xFAB2_0000` with
   the tag of the design it removes in bits `[15:0]`;
2. the frames, each a header, a data word per row and a check word;
3. the end word, and the CRC.

A check word, like the CRC, is the CRC-32 (zlib) of the words from the sync
word on, check words left out. The loader writes a frame into the latches only
after its check word matched, so a frame with a wrong bit never reaches the
fabric. A word before the sync word is dropped, and starts the watchdog. The generator writes the
streams; `seal` in `efpga_gen.py` is the format in code.

**The tag.** The generator gives each design a 16-bit tag, the first 16 bits
of the SHA-256 of its FASM (1 if they are 0), and sets it in the 16
configuration latches of the east edge that drive nothing inside the fabric
(`Config_accessC`, the features `X3Y<n>.L.C_bit<k>`). It sets the complement
of the tag, its check, in the 32 such latches of the west edge, twice
(`A_config_C` and `B_config_C`, the features `X0Y<n>.C.C_bit<k>` and
`X0Y<n>.D.C_bit<k>`, which the pad cells of a real pad ring could otherwise
use). `TAG` reads the tag. Like the rest of the configuration these latches
hold through a reset, so they say which design is in the fabric whatever the
wrapper's own state. A fabric holds a design when its tag is not 0 and both
copies of the check match it; latches that start at random do that about once
in 2^32. The loader refuses a stream whose design does not, and the generator
refuses a design that sets one of these latches itself and two designs of one
run with the same tag.

**Loading.** After `clear`, and out of reset when the fabric holds no design,
the loader writes 0 to every configuration latch and gives the fabric one
clock pulse.
With no configuration every logic cell is enabled and computes 0, so the pulse
puts every flip-flop of the fabric at 0. The loader then takes the words
written to `BITSTREAM` and writes one frame at a time. It sets `configured`
only after a frame on every strobe line, the end word, a matching CRC and a
tag with its check. Anything else sets `error`, with a cause:

| Cause | Meaning |
|---|---|
| 1 | a frame names a column the fabric does not have |
| 2 | the end word came before every strobe line had a frame |
| 3 | a check word or the CRC does not match |
| 4 | no word for `LOAD_TIMEOUT` cycles (65,536 by default) once a word was written, a stray one too, until a stream is whole |
| 5 | while a design is in the latches, a stream that is not its unload; or a loaded design without a tag and its check |

The frames before the refused one are in the latches, so the loader clears the
fabric again before it reports the error. A write to `BITSTREAM` waits while
the loader clears or strobes, at most five cycles, and after a refused load is
dropped until `clear`. `clear` is taken in every state. When it comes while
the strobes of a frame are high, the loader lowers them first and moves
`FrameData` a cycle later.

**Unloading.** A design that has run cannot be cleared safely
([Limits](#limits)); its unload stream removes it. While a design is in the
latches, a word other than the sync word is dropped, and the sync word starts
an unload: `configured` falls and the fabric is cut off from then on. The next
word must carry the tag the latches hold, or the stream is refused with cause
5 before a frame is written. The frames come in two parts (`unload_words` in
`efpga_gen.py`): first the frames that hold a cell's flip-flop selection, as
the design has them but with every cell on its flip-flop; then every frame of
the design with every LUT at 0 and the enable and reset of every flip-flop
back on their constants (`unload_fasm`), the routes, the tag and its check
unchanged. After the CRC the loader gives the fabric one clock pulse, which
puts every flip-flop at 0, and then clears it. STATUS, CONTROL and `TAG` are
then as after `clear`. A refused unload leaves the design in the latches, cut
off, with the error: the frames before the refused one are in, and the unload
can be sent again from its start.

Out of reset the loader keeps a fabric that holds a design, cut off, and waits
for its unload or a `clear`: STATUS reads 0 and `TAG` names the design. Any
other fabric it clears; a tag or a check that is unknown in simulation, `x`,
counts as none.

**Isolation.** The fabric is connected only while `configured` is set and
`isolate` is clear. Otherwise its clock is stopped, but for the one pulse of a
clear or of an unload; every input is 0, the user reset among them, which is
active low; and
every output is ignored, so the pads are released. While the fabric is
connected, a pad its design does not bind is not released
([Limits](#limits)).

**The user window.** MOSAIC's OBI response has no error signal, and a slave
that does not answer blocks the hart's data port. The hard part therefore
answers every request itself. While the fabric is isolated it answers in the
next cycle with `0xFAB00BAD` and sets `blocked`. When the user design does not
acknowledge within `BUS_TIMEOUT` cycles (256 by default) it answers with the
same value and sets `timeout`. It takes one request at a time. Every signal of
the window crosses a flip-flop in the hard part, to the fabric and back; the
pads pass through a gate only.

A user design meets the bus on the east edge of the fabric. Row `g` is the
`RAM_IO` tile at `Y(R-g)`, which has 16 inputs and 28 outputs:

| Signal | Width | Edge pins |
|---|---|---|
| `wdata` | 32 | inputs `[7:0]` of rows 0 to 3 |
| `valid`, `we`, `rst_n`, `be[3:0]`, `addr[9:2]` | 15 | inputs `[15:8]` of row 0, then of row 1 |
| `rdata` | 32 | outputs `[7:0]` of rows 0 to 3 |
| `ack` | 1 | output `FAB2RAM_C[0]` of row 0 |

`valid` stays high, with the address and the data stable, until `ack` is seen
high. `ack` must then fall before the next request starts; a request that
still finds it high when the timeout ends is answered by the hard part and
never reaches the design. The timeout runs from the grant, that wait
included, and an acknowledge in its last cycle is still an answer. Read data
is taken in the cycle `ack` is first high. A design acts once per request,
when it raises `ack`, and does not raise `ack` while `valid` is low. A
request that ends by `timeout` may still have reached the design: reset the
design (`CONTROL[1]`) before it is used again. A request that is open when
the fabric is cut off, by `isolate`, an unload or `clear`, is answered at once
with `blocked`, unless the design acknowledged it in that cycle; it may have
reached the design too. A request granted in the first cycle the fabric is
connected again waits one more: an acknowledge the design left high while it
was cut off shows only then, and must fall first. The window
passes `addr[9:2]`, so a design sees it repeat every 1 KB.
`tb/efpga/bus_regs_wrapper.v` shows the cells to instantiate. nextpnr names
them after their ports (`X3Y4.RAM2FAB_D0`), not by the letters of FABulous's
`bel.txt`.

### The order of the frames

A configuration is written one frame at a time, so the fabric passes through
configurations nobody designed. One of them can contain a loop that
oscillates: a LUT whose function or whose inputs are half written can feed
itself. A simulator has no delays to slow such a loop down and stops. This
was measured with `bus_regs` sent in `bit_gen`'s order to a cleared fabric:
Icarus hangs and Verilator ends with `DIDNOTCONVERGE`, both at the 36th of 80
frames. `counter8_en` loads in that order without it.

The generator therefore sends the frames in four passes. It first asks
`bit_gen` for the bitstream that only switches every logic cell to its
flip-flop output (`load_order/registered.bin`), and for the one that sets
every latch of a tag and its check (`load_order/tagged.bin`).

1. The frames of `registered.bin` alone: every cell output now comes from a
   flip-flop.
2. Every frame of the design, with those bits still set and the tag and its
   check at 0.
3. The frames that hold a flip-flop selection, as designed but for the tag.
4. The frames of the tag and its check, as designed.

The loader has put every flip-flop at 0 and keeps the clock stopped. Until
the third pass every cell output is therefore 0, and with all of them equal
nothing inside these fabrics can invert a signal (a pad cell inverts its
output enable on the way out). The third pass changes only where a cell's
output comes from, in a design that is complete, and the fourth only latches
that drive nothing in the fabric. Because the tag comes last, a fabric holds a
design only when every frame of it went in: a reset before the last pass
leaves no tag, and the loader clears what is there. When asked for a bitstream, the
generator refuses a fabric whose `bel.txt` names a cell type it does not
know, a `registered.bin` that does not set one bit per logic cell, and a tag
bit that is also a flip-flop selection. A stream has 639 words for either
design: 106 frames of six words, the sync word, the end word and the CRC,
against 406 words in `bit_gen`'s bitstream. The loader does not check the
order: it accepts any stream with a frame on every strobe line and matching
checks.

An unload goes the other way, from a design that has run: its flip-flops hold
values, so the cell outputs are not all 0. It changes four kinds of bit, and
nothing else: a cell's flip-flop selection (to the flip-flop), its LUT
function (to 0), its reset value (to 0), and the selection of its enable and
reset (to `VCC` and `GND`). It changes them in that order of kind, in two
parts.

1. The frames that hold a flip-flop selection, as the design has them but
   with every cell on its flip-flop. This only removes paths: a cell whose
   output comes from its flip-flop no longer passes its inputs on. Every
   configuration on the way, after each frame and each bit, is the design
   with paths removed, and a design without a loop of its own keeps none.
2. Every frame of the design with the other three kinds of bit changed. Every
   cell output now comes from its flip-flop, so a LUT function, a reset value,
   an enable or a reset reaches nothing but a flip-flop, whose clock is
   stopped: whatever order these bits change in, no signal of the fabric
   moves.

A LUT function changed before its cell's flip-flop is selected could make the
cell depend on an input the design leaves unused, which the default selection
of its input multiplexer still connects, and so close a loop: the first part
prevents that (the order was `bit_gen`'s, single pass, until a review on
2026-10-18 found this; for the two test designs that review's static analysis
found no such loop in that order either). When the frames are in, every cell output comes
from its flip-flop and every LUT computes 0, with its enable at 1 and its
reset at 0: one clock pulse puts every flip-flop of the logic cells at 0. The
flip-flops of the pad cells and of the east edge's inputs take inputs that
are 0 while the fabric is cut off. Those of the east edge's outputs keep a
value, but drive only outputs the wrapper ignores. From there on every signal
inside the fabric is 0 whatever the routes, and the clear that follows is as
safe as loading. An unload has 556 words: the sync and tag words, 12 frames
of the first part and 80 of the second, the end word and the CRC. The
generator checks that the unload switches every cell to its flip-flop; that
it changes no other bit rests on `unload_fasm`, which drops the features of
the LUT functions, the reset values and the enable and reset routes of the
logic cells (`L[A-H]_EN`, `L[A-H]_SR`, the names in the `LUT4AB` tile) and
adds the flip-flop selections. A comparison of the bitstreams of the two
designs, bit by bit, found only flip-flop selections and LUT bits changed;
neither design uses an enable, a reset or a reset value, so that part of
`unload_fasm` is not exercised.

## The tests

### The fabric alone

`tb/efpga/run.sh` generates the fabric and the bitstreams of the two designs.
It uses the one of an 8-bit counter with an enable and a reset (13 of the 64
logic cells), and builds
`tb_efpga_fabric.sv` around the fabric core with Icarus Verilog and with the
pinned Verilator. The bench is the loader. After loading it requires that
every strobe line was pulsed, releases the design, and compares the fabric's
pads with the counter's RTL in each of 600 cycles. In those cycles the count
wraps, is held for ten cycles with the enable low, is reset, and is held
through a reset that the low enable masks. The bench then checks the exact
final count.

Each simulator makes eight runs:

| Run | Expected |
|---|---|
| the bitstream, user clock stopped while loading | pass |
| the bitstream, user clock running while loading | pass |
| no bitstream | fail: the pad outputs differ |
| the bitstream with one truth-table bit flipped, in a LUT entry read only while the enable is low | fail: the pad outputs differ, from cycle 100 |
| the same, in an entry read only at the reset | fail: the pad outputs differ, from cycle 400 |
| the same, in an entry read only at the masked reset | fail: the pad outputs differ, from cycle 450 |
| the bitstream with one bit of a pad's output-enable selection flipped | fail: the output enables differ |
| the bitstream without its last frame | fail: a strobe line was never pulsed |

The step prints `TB PASS` once, after all sixteen runs gave the expected
result. A negative control that fails for another reason, such as a file that
cannot be opened, counts as a failure of the step, and so does a run that
lasts more than 120 s or that the simulator ends in any way other than the
bench's own verdict.

The controls show that three checks of the bench can fail: the comparison of
the pad outputs, the comparison of the output enables, and the check that
every strobe line was pulsed. The three single-bit controls of the counter
also show that the bench still applies and observes each part of its
stimulus: a bench that stopped before cycle 450 would let them pass. No
control makes the fourth check fail, the final count, which guards against a
comparison that passes because both sides stand still.

Two simulators are used because they start state differently. Icarus starts
every latch and every flip-flop at `x`; Verilator 5.050 starts them at 0. A
fabric that works only from one of them fails in the other. Only the Icarus
runs show that the reset at start-up brings the counter out of an unknown
state: in Verilator the counter starts at 0 without it. The reset in cycle
400, from a count of 133, is compared in both simulators.

## Limits

- **`clear` is unsafe on a design that has run; the unload is the way out.**
  Clearing the fabric zeroes every latch at once, and passes through
  half-cleared configurations as loading passes through half-written ones.
  Measured on 2026-10-13: after `bus_regs` has run, a `clear` stops both
  simulators (Icarus hangs, Verilator ends with `DIDNOTCONVERGE`), and zeroing
  one strobe line at a time stops them at the 43rd line. Measured again on
  2026-10-18 in Icarus, in step 6 of the wrapper bench: a `clear` where the
  unload is, and the unload without its clock pulse, both hang (cut at
  120 s); the unload as built does not. These two runs are not part of the
  sweep. A design that was configured and never connected is cleared without
  it. On silicon such a loop would ring until the remaining latches are
  written; nothing here measures that, nor whether the latches settle when
  the clock pulse of an unload or of a clear meets them.
- **A reset keeps whatever holds a tag and its check.** Out of reset the
  loader keeps such a fabric and waits for its unload. On silicon the latches
  start at random; 48 of them must agree for a random start to be kept, which
  happens about once in 2^32, and firmware that finds a tag it does not know
  has only `clear` for it. The 32 latches of the check are the configuration
  outputs of the west edge, which a pad ring could otherwise use. Two designs
  can share a tag: the generator refuses that within one run, but between
  runs one pair in 65,536 does, and the unload of one would then be taken for
  the other. A reset from the strobe of a stream's last frame until its clear
  (as long as the writer takes to send the end word and the CRC, at most
  `LOAD_TIMEOUT` cycles, then two more) keeps the stream whether it would
  have been accepted or refused; a reset before a refused stream is cleared
  keeps it when it was complete (refused for its coverage or its CRC): its
  unload or `clear` removes it, and it never ran. A reset in the middle of an
  unload keeps the design partly unloaded; sending its unload again was tested
  in Icarus in 11 runs by the review of 2026-10-18 (7 during the unload, 4
  in its clear), on the RTL before the check of the tag, not in the sweep.
- **A refused load is cleared without its unload.** A frame goes into the
  latches only after its check word, so what a refused stream leaves behind
  is the start of a correct one, which the loader then clears. Before the
  third pass that is safe for the same reason loading is; a stream refused
  later (cause 2, 3 at the CRC word, or 5) leaves a whole design, never run,
  and its clear is safe only as far as the clear of such a design was
  measured. Measured on 2026-10-13 on the full-SoC model, before the check
  words: one of 70 random single-bit flips of the `bus_regs` stream, in the
  column field of a frame header of the first pass, stopped the simulator.
  Measured again on 2026-10-18 on the wrapper bench in Icarus, with 70 other
  random flips of the new stream (a one-off script, seed
  20261018), given where the bench expects a refused stream: none stopped the
  simulator. 69 were refused for a check word or the CRC; one, in the sync
  word, never started a stream, so nothing was written; the loader was still
  waiting, and would have given up with cause 4. Neither measurement is part of the sweep.
- **The frame order is argued, not proved.** It rests on three facts read in
  the RTL of these tiles: an unconfigured cell is enabled, a cell's output
  comes from its LUT or from its flip-flop, and inside the fabric nothing but
  a LUT, or a wide multiplexer with unequal inputs, can invert a signal. A
  design synthesised with flip-flop enables or resets routed through the
  fabric (Yosys's `-complex-dff`, which the generator does not pass) was not
  tried.
- **A pad the design does not bind is driven.** The output enable of a pad
  cell is the inverse of a routed signal, and with nothing routed there it
  follows whatever the fabric's default route carries. Measured on
  2026-10-13 with `bus_regs`, which binds no pad: once connected, between
  four and seven of the eight output enables were high, and they changed with
  the value written to a register. The wrapper has no mask for the pads. A
  design must bind every pad and hold the enable of those it does not use, as
  `counter8_en` does, and the SoC test leaves the pads unconnected.
- **What the wrapper is not.** It has one OBI slave port, a slave of the
  system crossbar like the SoC's other slaves. It cannot master the bus and
  raises no interrupt. It was never synthesised: there is no
  area, no timing and no layout, and its clock gate is the generic cell
  model.
- **What the wrapper's tests do not check.** One fabric, three designs, two
  cores: the load is run by a cv32e20, from SRAM by the test firmware and
  from flash by the production firmware, and by SERV from flash. Only `shell_regs`, the
  third design, uses the byte enables, and its check writes one byte.
  Address bits 9 to 3 are checked where they enter the fabric and are used by
  no design. The watchdog is tested at 512
  cycles, not at its default. The wrapper is reset in the middle of a load,
  before its last pass, and with a design in the latches before and after it
  ran, but not in the middle of an unload. The test firmware unloads only
  `bus_regs`, from SRAM, with no reset; the production firmware unloads
  `shell_regs` from flash after one warm reboot (`efpga_design`), and never a
  design other than the one packed. No design is slower than the bus timeout,
  and
  `bus_regs` holds its read data steady, so no test shows that read data is
  taken in the cycle the acknowledge rises and in no other.
- **What the bench of the fabric does not check.** The design is one counter. Its output
  enables are constants, so no logic of the fabric drives one. The `RAM_IO`
  edge is not exercised: its inputs are tied to 0 and its outputs are not
  read. The inputs of six of the eight pads stay at 0. A wrong bit in a
  resource the counter does not use changes nothing and is not detected, and
  not every wrong bit in a resource it does use is. Measured once, on
  2026-10-13, with the bench in Icarus and the user clock stopped while
  loading: of the 718 configuration bits of the resources the counter uses
  (the selection bits of its multiplexers and the bits of its 13 logic
  cells), a single flipped bit is detected in 587 cases and not in 131. Nine
  of the 587 are detected because the fabric then oscillates and the run is
  cut at 120 s. Many of the 131 are in functions the counter never uses, such
  as a truth-table entry behind an unused LUT input, or the reset value of a
  fabric flip-flop whose own reset input the design does not use (the
  counter's reset is built from LUTs); the others were not analysed. This
  measurement is not part of the sweep.
- **Size.** The fabric of FABulous's default template (14 logic rows by 10
  columns, 69,482 latches) did not build with Verilator 5.050 on the
  development machine (12 GB, no swap): `verilator --cc` aborted with
  `std::bad_alloc` at a peak of 4.0 GB resident in one run, and at 3.4 GB in a
  run capped near 3.4 GB of address space. Icarus compiled it with a 2.3 GB
  peak; the compile and four runs took 388 s with the pinned Icarus. This was
  measured on 2026-10-12 with FABulous's 16-bit counter example and is not
  part of the sweep. Larger presets need a measurement before they are
  offered.
- **Verilator and unconfigured latches.** Verilator 5.050 simulates this
  fabric with every latch starting at 0. With a latch model that starts at
  random, every run stopped before the first time step with `DIDNOTCONVERGE`.
  A wrong bitstream can do the same, or make Icarus loop without advancing
  time. The wrapper writes 0 to every latch as it leaves reset unless the
  latches hold a design, but until then the SoC test depends on the start at
  0, so the Verilator pin matters there too. The wrapper bench passes in Icarus, where every latch starts
  at `x`.
- **No timing.** nextpnr 0.9 reads `bel.v2.txt`, which has no delay lines, and
  does not read `bel.v3.txt`, where FABulous writes cell delays. The cell
  delays in `nextpnr.log` (3.0 ns through a LUT, 2.5 ns setup, 1.0 ns clock to
  output) are the same figures `bel.v3.txt` holds, and `pips.txt` gives every
  routing switch the same delay. None of them comes from a cell library or a
  layout, so the delays and the maximum frequency in `nextpnr.log` are not a
  timing result. `sdf-timing` is the PyPI release, not the commit FABulous
  pins; only FABulous's timing-model flow parses SDF with it.
- **A tool combination FABulous does not test.** FABulous 2.2.0's own
  environment pins other Yosys and nextpnr revisions. The evidence that 2.2.0
  works with Yosys 0.62 and nextpnr 0.9 is the seven sweep steps.
- **One preset.** The benches and the wrapper's edge signals are written for
  `small`: 8 pads, and at least four `RAM_IO` rows. The four single-bit
  controls of the fabric bench are fixed positions in the counter's
  bitstream, which the pinned tools reproduce bit for bit; after a tool change
  they have to be chosen again.
- **Platform.** Only x86_64 Linux was tried.
