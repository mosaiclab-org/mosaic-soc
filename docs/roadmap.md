# Roadmap

What is planned, grouped by theme. Nothing listed here exists yet; the eFPGA
section names what of it does. What does exist is in
[status.md](status.md).

## Widen the design family

- Prove Ibex, cv32e40p and cv32e40px in the complete SoC, or mark them
  unsupported.
- Bring QERV into the full-SoC regression.
- Expose more peripherals. The platform can instantiate blocks that the
  configuration cannot yet name, and adding them changes the memory map.
- Qualify a second bus fabric physically, or state that OBI is the only one.
- Caches, and accelerators as first-class configuration entries.

## A second and third technology

- Finish IHP sg13g2: an area calibration from a real run, corner names end to
  end, then one complete signoff.
- Port to sky130 to show that the technology store generalises.
- Routability records per technology. The demonstrated densities follow the
  metal stack and do not transfer from GF180MCU.

## Power evidence

- Compute energy per cycle from a simulated workload instead of the timing
  tool's default switching activity. The workload capture exists
  (`harness/evidence/workload.py`); it is not yet the basis of the objective.
- A catalogue of SRAM macros so that memory choices can be searched.

## The improvement loop

- More settings for the line search: the capacitance repair margin, antenna
  repair iterations, the synthesis fan-out limit.
- Re-check the clock after a density change. The two interact and the search
  treats them as independent.
- Search over several settings at once, when enough single-setting experiments
  exist to know which interact.
- Walk the density of Block B, and the clock of Block C.
- Housekeeping: timestamps in the search journal, a disk pruning policy, and a
  way to re-measure run-to-run variation after a tool change.

## eFPGA

Four phases exist ([efpga.md](efpga.md)). Two FABulous
fabric presets, 4x4 and 8x8, are generated by pinned tools; the first is
simulated alone with a real bitstream. A wrapper makes it a bus peripheral
with MOSAIC's own configuration loader, and the key `soc.efpga` puts both in
the generated SoC: firmware writes a bitstream through a register, uses two
registers of the user design, removes the design with its unload stream and
loads it again; a request before configuration and a design that never answers
are both answered by the wrapper, and a reset keeps a design that has run. One
command takes a user's Verilog, written against the shell of the preset, to a
simulation in which the production firmware loads it from flash before it
wakes the workers, on each bus, with a SERV hart 0, and on both presets; the
fabric's pads reach their pins through pad_control. The wrapper and the
`small` fabric synthesise for GF180MCU, with no negative slack at 20 MHz
before layout. Beside the cores, the fabric is a worker slot of the TDU: a
push with its `core_hint` wakes it, it takes the descriptor from the TDU's
queue, hands the task to the design and sleeps again when the design ends it,
and the TDU parks it when it does not. What follows does not exist.

- **Silicon.** A signoff-clean design that contains a fabric.

Open: which presets are offered, and the technology, GF180MCU or another.

## Verification depth

These come before new features, in this order; the eFPGA phases above are the
one feature started alongside them. Each one ends as a step of the
regression sweep.

- A C program built with the generated start-up code, as the base for the
  tests below.
- Boot from SRAM without the testbench writing the RAM: the boot ROM's copy
  from flash, and the orchestrator firmware's SRAM builds with a complete
  start-up, on every core that can be an orchestrator.
- A test for every peripheral: GPIO, the timer, the SPI host, I2C, the serial
  link and the UART's receive pin, then the always-on blocks.
- Interrupt delivery in the complete SoC: a CLINT and a PLIC interrupt on each
  core that declares the capability, the TDU interrupt and a full TDU queue.
- The JTAG debug module driven in simulation.
- Core tests beyond liveness: the M and C extensions and RV64 on the cores
  that have them.
- The two memory profiles that software generation refuses, and `soc.dma:
  xheep` made to select X-HEEP's DMA or removed.
- The sweep run automatically on every change, with the software tests on the
  pinned toolchain and a success marker that a failure line cannot match.

- Decide whether gate-level simulation becomes a signoff hard check.
- Make the equivalence check return a verdict.
- Longer gate-level runs, and gate-level simulation of Block B at 20 MHz.
- Raise the flow timeouts that are shorter than a cold RTL generation.

## Agent tooling

- Measure the text-to-configuration path with small local language models. The
  evaluation set and its scoring are in place (`./mosaic config-author eval`).
- Grow the evaluation set with requests written by people who did not write the
  grammar.
- Constrain model output with a JSON schema where the provider supports it.
- Verify a live model session in each supported host.
- Expose the remaining skills (preflight, waiver audit, netlist comparison,
  gate-level triage, technology porting) as gated tools.

## The generator as a compiler

- An explicit intermediate representation between the configuration and the
  templates. The first half, a typed view of the design intent, exists in
  `harness/intent.py`.
- Platform backends beyond the microcontroller shape: a clustered design and an
  application-class design with coherent caches.
- Catalogues that record, as data, which core is qualified on which technology
  and at which corner.
